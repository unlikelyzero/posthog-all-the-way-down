2:00 · The problem

A protocol test is a cache

  • It's a cached model of what the frontend used to send.
  • Nothing invalidates that cache. No error, no failing check, no 404.
  • Code review sees "removed a debounce."
    It can't see "list endpoint load ×5–6.5", or that api.js didn't change with it.
  • PostHog deploys every merge to master. The cache goes stale on every merge.

Source: PostHog handbook, "Development process" page.

2:00–4:00. SAY: "A protocol test is a recording of what the frontend sent on the day somebody wrote it. That's a cache. And the painful thing about this cache is it never throws a miss. It just keeps serving yesterday." Debounce example: "The diff is one line. Reviewer approves it, correctly. Nobody asks what it does to the load profile." PostHog: "Our hosts deploy every merge to master, per their own handbook. So the gap between frontend and load test opens continuously." 5:30 · Scoring

Four independent gates

wr = browser share of calls to route r (pooled over R runs)  ·  qr = protocol share

GateFormulaThresholdCatches
Coverage CΣ wr · [qr > 0]≥ 0.95 + critical routesnew routes (N+1)
Mix M1 − ½ Σ |wr − qr|≥ 0.85volume shifts (debounce)
Stale Eshare of protocol calls not in reference, or 404/410≤ 0.02removed / renamed routes
Errorsprotocol non-2xx/3xx rate≤ 0.01a broken test
  • Each gate passes or fails on its own. A good mix must not hide 404s.
  • Thresholds set just past the worst of 5 baseline runs. Not chosen by feel.
5:30–6:30. SAY: "Four checks. Coverage: what fraction of browser traffic lands on routes the protocol test hits at all. Mix: one minus total variation distance. 1 means identical distributions, 0 means disjoint. Stale: protocol calls to routes the browser no longer makes. Errors: the test itself is broken." Key point: "They're independent. No combined score gates anything, because a great mix shouldn't hide a pile of 404s." Calibration: "Ran the unchanged baseline 5 times, set each threshold just past the worst baseline value. Then checked each seeded drift fails the gate it should." (Not done yet: say 'calibrated from 5 baseline runs' only once it's true.)
6:30 · One key, both sides

Route key & the PostHog cross-check


// k6/route.js: imported by journey.js, api.js and score.js
routeKey = METHOD + ' ' + template(pathname)          // numeric or ≥8-char hex/uuid segments → :id
         + (pathname.endsWith('/query/') ? '#' + body.query.kind : '')
  

SELECT s.attributes['http.request.method'] AS method,
       s.attributes['url.template']        AS route,
       sum(m.count)                        AS calls  -- histogram rows are pre-aggregated
FROM posthog.metrics AS m
JOIN (SELECT series_fingerprint, any(attributes) AS attributes
      FROM posthog.metric_series GROUP BY series_fingerprint) AS s
  ON m.series_fingerprint = s.series_fingerprint
WHERE m.metric_name = 'http.client.request.duration'
  AND m.service_name = 'posthog-app'
  AND s.attributes['meetup.run_id'] = {run_id}       -- per run, not a time window
GROUP BY method, route

template() copies posthog-js network-metrics, so keys match url.template. The UI puts the query kind in the path, so url.template sees it too; #kind only matters for a bare /query/. Baseline run: 100% agreement per route. 20 s deadline, then "pending".

6:30–7:00. Fast slide. SAY: "Everything hinges on one route key, shared by all three scripts so it can't drift. The templating rule is copied from posthog-js, so our keys match PostHog's url.template exactly. The UI sends the query kind in the path, POST /query/HogQLQuery/, so PostHog's url.template separates kinds too. The #kind suffix only matters for clients that post to a bare /query/, where the kind is only in the body." HogQL: "This is the query against PostHog's own metrics. 14:00 · Evaluating the agent

Did the agent fix it, or memorize it?

  • 3 scenarios × 5 trials × with k6 MCP vs shell k6 only = 30 runs
  • Agent sees a drift report from training references.
    Graded on held-out browser runs with different search terms.
  • Realism gates, so it can't replay the route list:
    setup() auth · scenarios > 1 VU · sleep() · check() · no copied IDs · search terms from an array
  • Tool order from stream-json: validate_script before run_script?

Same shape as PostHog's own MCP evals (services/mcp/evals/README.md).

19:00 · Takeaways
  1. Your load test is a cached model of the frontend. Check it for staleness.
  2. Compare it with real browser traffic: independent gates, calibrated thresholds.
  3. Let agents fix it, and eval the agent: with vs without the tools, on held-out data.
A protocol load test is a cached model of browser behavior. Keep comparing it with observed browser traffic, or a green test may be generating yesterday's load.

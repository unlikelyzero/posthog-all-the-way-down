Thirty-second primer

What is Grafana k6?

Open-source load testing. Tests are JavaScript; the engine is Go. Each virtual user (VU) runs your script in a loop.

Protocol VUs: raw HTTP, cheap, thousands per machine


import http from 'k6/http'
import { check, sleep } from 'k6'

export const options = { vus: 50, duration: '1m' }

export default function () {
  const res = http.get(`${BASE}/api/feature_flags/`)
  check(res, { ok: (r) => r.status === 200 })
  sleep(1)
}

Browser VUs: real Chromium, real clicks, expensive


import { browser } from 'k6/browser'

export default async function () {
  const page = await browser.newPage()
  await page.goto(`${BASE}/feature_flags`)
  await page.locator('input').type('checkout')
  await page.close()
}

Load tests run mostly protocol VUs. So someone has to write down what the browser sends.

[~1:00, 30 s] For anyone who hasn't used it: k6 is Grafana's open-source load tester. You write the test in JavaScript and a Go engine runs it, each virtual user looping over your default function. Two kinds of VU. Protocol VUs send raw HTTP: cheap, you can run thousands. Browser VUs drive a real Chromium: faithful, but expensive. Click: so real load tests are mostly protocol VUs, which means someone hand-wrote the list of requests the browser makes. Hold that thought.

The problem

A protocol test is a cached model of what the frontend used to send.

Nothing tells you when the cache goes stale.

  • Code review sees "removed a debounce". It doesn't see the new load profile.
  • PostHog deploys every merge to master.

Source: PostHog Handbook, Engineering › "Development process"

[2:30 to 4:00] A protocol test is a cached model of what the frontend used to send. Someone recorded or hand-wrote it once. Nothing invalidates that cache. Click. Code review can see a debounce was removed. It can't tell you what that does to the load profile, or whether anyone updated the load test. Click. And here, at PostHog, every merge to master deploys. Cite the handbook's development-process page. The cache goes stale all the time.

[4:00 to 5:30] The reference journey: k6 browser drives the real UI (flags page, type a search, open a flag, open a dashboard) and records every API call with page.on('request'). The UI puts the query kind in the path (POST /query/HogQLQuery/), so each kind is its own route; only a bare /query/ POST needs the kind read from the body. Click. PostHog sees the same calls in its own network metrics: PostHog recording PostHog. We show it next to the score as a cross-check; on a baseline run it agrees 100% per route with the browser capture. It never gates the build: the browser capture is the ground truth, it's immediate, and it doesn't depend on ingestion lag or an alpha product.

The idea, part 2

Score the protocol test against it

GateQuestionPass ifCatches
CoverageDo we hit the routes the browser hits?≥ 0.95new routes
MixIn the same proportions?≥ 0.85volume shifts
StaleAre we calling routes that are gone?≤ 0.02removed routes
ErrorsIs the test itself failing?≤ 0.01a broken test

Independent pass/fail. Thresholds calibrated from 5 baseline runs, not vibes.

"This is a journey contract, not a model of your whole user population."

[5:30 to 7:00] Three checks, each pass/fail on its own. Coverage: weighted share of browser routes the protocol test hits. Mix: how close the proportions are (one minus total variation distance). Stale: share of protocol calls to routes the browser never makes, or that 404. Independent on purpose: a good mix must not hide 404s. No combined score gates anything. Thresholds: ran the unchanged baseline five times, set each threshold just past the worst baseline value. Click. Say it plainly: this is a journey contract, not a model of your whole user population.

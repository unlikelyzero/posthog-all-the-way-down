The obvious fix

Why not just run thousands of Grafana k6 browsers?

Protocol VU

1.7 MB

0.1 CPU-seconds per journey

Browser VU (real Chromium)

1.55 GB

11 CPU-seconds per journey

~900× the memory. ~100× the CPU. Same journey.

1,000 browser VUs ≈ 1.5 TB of RAM. So load tests stay protocol, and protocol tests drift.

Measured here: same journey, Grafana k6 v2.3, peak memory of Grafana k6 + Chromium, 3 runs each. Grafana: protocol VUs use ~1–5 MB (Running large tests); Grafana Cloud bills browser VUs at 10× for their resource use.

[30 s] The obvious question: if the browser is the truth, why not load test with browsers? Because a k6 browser VU is a real Chromium. Measured on this laptop, running the exact same journey: a protocol VU peaks at 1.7 MB, a browser VU at 1.55 GB. About 900 times the memory, about 100 times the CPU. A thousand browser VUs is a terabyte and a half of RAM. Grafana's own guidance is the hybrid: mostly protocol VUs, a handful of browser VUs. So the load stays protocol, and protocol tests drift. Sources: grafana.com/docs/k6/latest/testing-guides/running-large-tests/ (~1-5 MB per protocol VU); grafana.com/docs/grafana-cloud/testing/k6/author-run/vu-hours/ (browser VUs billed at 10x).

[4:00 to 5:30] The reference journey: k6 browser drives the real UI (flags page, type a search, open a flag, open a dashboard) and records every API call with page.on('request'). The UI puts the query kind in the path (POST /query/HogQLQuery/), so each kind is its own route; only a bare /query/ POST needs the kind read from the body. Click. PostHog sees the same calls in its own network metrics: PostHog recording PostHog. We show it next to the score as a cross-check; on a baseline run it agrees 100% per route with the browser capture. On a PR it never gates the build: the browser capture is immediate and doesn't depend on ingestion lag. But that agreement is what lets PostHog take over in production, where it has real users. Later we point the scorer at it directly.

The idea, part 2

Score the protocol test against it

GateQuestionPass ifCatches
CoverageDo we hit the routes the browser hits?≥ 0.95new routes
MixIn the same proportions?≥ 0.85volume shifts
StaleAre we calling routes that are gone?≤ 0.02removed routes
ErrorsIs the test itself failing?≤ 0.01a broken test

Independent pass/fail. Thresholds calibrated from 5 baseline runs, not vibes.

[5:30 to 7:00] Three checks, each pass/fail on its own. Coverage: weighted share of browser routes the protocol test hits. Mix: how close the proportions are (one minus total variation distance). Stale: share of protocol calls to routes the browser never makes, or that 404. Independent on purpose: a good mix must not hide 404s. No combined score gates anything. Thresholds: ran the unchanged baseline five times, set each threshold just past the worst baseline value.

Three things to take home

1

A green load test can be testing yesterday's app.

One PR: the browser went from 4 to 20–26 flag-list calls. The load test sent 4, and passed.

2

Score it against what users actually send.

A Grafana k6 browser on a PR, PostHog in production. The same gates catch drift and tests in the wrong part of the app.

3

Let an agent keep it current.

PostHog MCP: what users do. Grafana k6 MCP: validate and run the fix. Then check it really used them.

Grafana k6 makes the test match your users. PostHog shows you who they are now.
Keep them in sync, or a green test is generating yesterday's load.

[~1 min] Three takeaways, one click each. One: a green load test can be testing yesterday's app. Our one PR took the browser from 4 to 20 to 26 flag-list calls; the load test kept sending 4 and kept passing. Two: score it against what users actually send. On a PR a k6 browser plays the user; in production, PostHog's network metrics are the users. The same gates catch drift, and a test aimed at the wrong part of the app. Three: let an agent keep it current. The PostHog MCP tells it what users do, the k6 MCP validates and runs the fix. And check it actually used them: offered the k6 MCP alone, our agent ignored it. Click. The close, read slowly: Grafana k6 makes the test match your users. PostHog shows you who they are now. Keep them in sync, or a green test is generating yesterday's load. If asked about limits: request bodies beyond the query kind aren't compared, latency fidelity isn't measured, the k6 reference is one journey, the PostHog reference has no per-page filter, and PostHog's metrics product is alpha.

A load test is a cache.

[2:00 → 2:25] SAY: "A protocol load test is a cache. At some point somebody looked at what the frontend sends, wrote it down as HTTP calls, and froze it." "It's a cached model of browser behavior."

Caches go stale.

[2:25 → 2:45] SAY: "And caches go stale. Every frontend change can change what the browser sends: new routes, more calls, different query types. The script doesn't change with it."

Nobody invalidates this one.

[2:45 → 3:10] SAY: "Your CDN cache has a TTL. Your query cache has invalidation. This cache has nothing. Nothing tells you when it's stale. It just keeps passing."

Review sees the diff.
Not the load.

[3:10 → 3:35] SAY: "Code review can see that someone removed a debounce. It's right there in the diff. What review can't tell you is what that does to the load profile, or whether the load test changed with it. Usually it didn't."

Every merge ships.

[3:35 → 4:00] SAY: "And at PostHog, every merge to master deploys. That's in their public handbook, on the development-process page. So the cache doesn't go stale once a quarter. It can go stale many times a day." CITE: posthog.com/handbook/engineering/development-process

Record the real browser.

[4:00 → 4:40] SAY: "So here's the idea. Keep a reference journey: k6 browser drives the real PostHog UI and records every API call with page.on('request'). Query calls carry their query type in the URL, POST /query/HogQLQuery/ and so on, so each kind of query is its own route." "That's the ground truth. It's deterministic, it's immediate, and it sees request bodies."

PostHog sees it too.

[4:40 → 5:15] SAY: "And because this is PostHog, the same calls show up in PostHog's own network metrics. PostHog, recording PostHog, being tested by k6." "I use that as a cross-check, not the judge. On a baseline run it agrees with the browser capture 100%, route by route. If ingestion is late, the check still works. Metrics is also an alpha product, so I don't want it on the critical path."

independent gates

[5:40 → 6:15] SAY: "Three checks, each pass or fail on its own. Plus a fourth, the test's own error rate, so a broken script can't pass." "Coverage: does the load test hit the routes the browser hits? Catches new routes." "Mix: are the proportions right? Catches volume shifts." "Staleness: is the load test calling routes that are gone, or 404ing? Catches removed or renamed routes." "They're independent on purpose. A combined score could let good mix hide a pile of 404s. You'll see in the demo why that matters."
5

baseline runs

[6:15 → 6:40] SAY: "The thresholds aren't chosen by feel. I ran the unchanged baseline five times, five browser references against five protocol runs, and set each threshold just past the worst baseline value, with a small margin." "Then I checked that each injected change fails the gate it's supposed to fail."

"Doesn't this already exist?"

[17:00 → 18:15] Answer the room's question before they ask it. - "k6 Studio can regenerate the test from a recording." Yes. This tells you WHEN to regenerate. - "Just run browser VUs at load." Grafana recommends mostly protocol VUs plus a few browser VUs, for cost. This keeps the protocol side honest. - "Why PostHog, not Faro, Beyla or OTel?" Any real-user telemetry works. The comparison method is the point. - "PostHog already has session replay's network tab, alerts, self-driving fixes." Replay is one session at a time. Alerts tell you traffic changed, not what's stale in your test. Self-driving fixes product code, not test code. CUT IF LONG: skip this slide and the next, take them in Q&A (saves 2 min).
